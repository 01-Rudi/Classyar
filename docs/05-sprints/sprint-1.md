> «در این Sprint، MVP اولیهٔ کلاس‌یار را با شروع پیاده‌سازی قابلیت‌های پایه تحویل می‌دهیم: ثبت‌نام و ورود کاربران، مدیریت اطلاعات پایه، آپلود جزوه، نمایش فهرست جزوه‌ها، مشاهدهٔ جزئیات و دانلود جزوه و مدیریت جزوه‌های شخصی.»

## ۸. Retrospective

### Start (شروع کنیم)

- ثبت وضعیت پیشرفت هر User Story
- نوشتن و اجرای تست برای قابلیت‌های پیاده‌سازی‌شده
- ثبت وظایف و موانع در GitHub Issues

### Stop (متوقف کنیم)

- اعلام تکمیل قابلیت بدون بررسی و تست
- شروع پیاده‌سازی بدون توافق دربارهٔ نیازمندی‌ها
- ثبت‌نکردن تصمیم‌های فنی تیم

### Continue (ادامه دهیم)

- مستندسازی پروژه
- استفاده از GitHub برای مدیریت کد و تغییرات
- بازبینی مستندات و هماهنگی اعضای تیم

---

## ۹. درس‌های آموخته‌شده

۱. نیازمندی‌ها باید پیش از پیاده‌سازی بررسی شوند تا معیار تکمیل هر Story روشن باشد.

۲. وضعیت مستندات و وضعیت پیاده‌سازی باید جداگانه ثبت شوند.

۳. قابلیت‌های MVP باید به بخش‌های کوچک و قابل‌آزمایش تقسیم شوند.

۴. تصمیم‌های فنی باید با توافق تیم ثبت شوند.

۵. تست و بازبینی کد باید بخشی از فرایند توسعه باشند.

## ۱۰. برنامهٔ Sprint بعدی

Sprint Goal:

> «در Sprint 2، قابلیت‌های جست‌وجو و فیلتر جزوه‌ها، امتیازدهی به جزوه و استاد، ثبت نظر و پاسخ و صفحهٔ استاد را توسعه می‌دهیم.»

Storyهای انتخاب‌شده:

- US-07: جست‌وجو و فیلتر جزوه‌ها
- US-08: امتیازدهی به جزوه
- US-09: ثبت نظر و پاسخ به نظر
- US-10: مشاهدهٔ صفحهٔ استاد
- US-11: امتیازدهی به استاد

ریسک‌های پیش‌رو:

- وابستگی قابلیت‌ها به تکمیل Sprint 1
- یکپارچه‌سازی رابط کاربری و API
- اعتبارسنجی داده‌ها و تست قابلیت‌ها
