## ۲. نمای کلی معماری

### ۲.۱ سبک معماری
**Monolith + Layered Architecture**

- یک برنامهٔ واحد
- سه لایهٔ اصلی: Presentation، Business، Data
- مناسب تیم کوچک (۵ نفر) و پروژهٔ ۱۴ هفته‌ای
- ساده برای شروع، قابل گسترش

### ۲.۲ دیاگرام لایه‌ها

```
+------------------------------------------+
|  Presentation Layer                      |
|  React (SPA)                             |
+---------------------+--------------------+
                      | HTTP / REST (JSON)
+---------------------v--------------------+
|  Business Layer                          |
|  Node.js + Express                       |
+---------------------+--------------------+
                      | Prisma (SQL)
+---------------------v--------------------+
|  Data Layer                              |
|  PostgreSQL + File Storage               |
+------------------------------------------+
```

### ۲.۳ جریان داده
کاربر ← مرورگر (React) ← API (Express) ← پایگاه داده (PostgreSQL) و ذخیرهٔ فایل

درخواست از کاربر به Frontend، سپس به API و در پایان به پایگاه داده می‌رسد؛ پاسخ همین مسیر را برمی‌گردد.

## ۴. تصمیم‌های معماری (ADR)

### ADR-01: چرا Monolith؟

**تصمیم:** معماری Monolith

**دلیل:**
- تیم کوچک (۵ نفر) و زمان محدود (۱۴ هفته)
- پیچیدگی کم و یک زبان (JavaScript) برای کل تیم
- سرعت توسعه بالاتر
- استقرار ساده

### ADR-02: چرا React؟

**تصمیم:** React برای Frontend

**دلیل:**
- محبوب و مستند
- اکوسیستم بزرگ
- SPA برای تجربهٔ کاربری بهتر در جست‌وجو و فیلتر

### ADR-03: چرا PostgreSQL؟

**تصمیم:** PostgreSQL برای Database

**دلیل:**
- رابطه‌های استاد، درس، واحد و جزوه رابطه‌ای هستند
- قیدهای یکتایی (یک امتیاز برای هر کاربر) به‌سادگی اعمال می‌شود
- رایگان و اوپن‌سورس

### ADR-04: ذخیرهٔ فایل جزوه‌ها

**تصمیم:** فایل‌ها روی دیسک سرور ذخیره می‌شوند و مسیر آن‌ها در PostgreSQL می‌ماند. دسترسی از طریق یک لایهٔ جداگانه (Storage Service) است.

**دلیل:**
- ساده‌ترین راه برای MVP
- با جداسازی لایه، گذر به سرویس ابری بدون تغییر در بقیهٔ کد ممکن است
- محدودیت: فضای دیسک (حداکثر ۲۰ مگابایت برای هر فایل)

## ۶. امنیت

### ۶.۱ احراز هویت
- **JWT** برای API
- **bcrypt** برای رمزنگاری گذرواژه (حداقل ۸ کاراکتر)
- **Refresh Token** برای تمدید

### ۶.۲ مجوزدهی
- **Role-Based Access Control (RBAC)**
- نقش‌ها: Student، Professor، Admin (و مهمان بدون توکن برای مشاهده)
- استاد فقط به جزوه‌های مربوط به درس خودش دسترسی دارد
- حساب استاد پس از تأیید مدیر فعال می‌شود

### ۶.۳ امنیت API
- **HTTPS** اجباری
- **Rate Limiting** (۱۰۰ درخواست در دقیقه)
- **CORS** محدود
- **Input Validation** با Zod

### ۶.۴ امنیت فایل و محتوا
- فقط PDF، JPG، PNG و DOCX تا ۲۰ مگابایت؛ نوع فایل از محتوای آن بررسی می‌شود، نه فقط پسوند
- نام فایل پاک‌سازی می‌شود و فایل خارج از مسیر عمومی ذخیره می‌شود
- لینک گروه فقط با ساختار `https` ذخیره می‌شود
- نظرها قبل از نمایش برای جلوگیری از XSS پاک‌سازی می‌شوند

## ۷. مقیاس‌پذیری

### ۷.۱ محدودیت‌های فعلی
- Monolith ← مقیاس‌پذیری محدود
- یک سرور ← تک نقطهٔ شکست
- ذخیرهٔ فایل روی دیسک ← با رشد جزوه‌ها فضا کم می‌شود
- هدف فعلی: ۱۰۰ کاربر همزمان (NF-02)

### ۷.۲ مسیر رشد
1. فاز ۱ (MVP): Monolith + یک سرور + ذخیرهٔ فایل روی دیسک
2. فاز ۲: انتقال فایل‌ها به سرویس ذخیرهٔ ابری
3. فاز ۳: Load Balancer + چند سرور
4. فاز ۴: Database Replication و جدا کردن سرویس‌های پرمصرف
